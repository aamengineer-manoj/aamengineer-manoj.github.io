A conversational engine that answers from your own documents.

My MTech dissertation: a multi-turn, retrieval-augmented chat system built entirely on open-source models, with a measurable way to compare them.

View the code on GitHub
the problem

Why this project.

Companies keep policies, API guides and runbooks across many tools, and employees still struggle to find answers. Language models are fluent but can invent facts and know nothing about private documents. Retrieval-augmented generation (RAG) fixes part of that by giving the model relevant passages first.

The harder part is the conversation. A follow-up like "what about business accounts?" means nothing alone, and a long chat eventually overflows the model's prompt. This project tackles both.

how it works

One turn, end to end.

01 / ingest

Semantic chunking

Documents are split by headings and paragraphs, then merged by embedding similarity so each chunk keeps one topic.

02 / retrieve

Query-aware retrieval

The previous question is added before searching, so follow-ups find the right passages. FAISS finds the closest chunks, and a tuned score threshold drops weak matches.

03 / answer

Grounded prompt

Retrieved knowledge, conversation history and the current question are labelled clearly in the prompt. If nothing relevant is found, the engine says so in code instead of letting the model guess.

04 / remember

Bounded memory

Recent turns stay word for word while older ones roll into a short summary, so the prompt stays small in long chats.

the build

What I built.

stack

Fully open source

Python, Hugging Face Transformers, Sentence-Transformers, FAISS and Streamlit. No paid APIs, and it can run offline.

models

Two backends, one interface

Qwen2.5-1.5B-Instruct and TinyLlama-1.1B-Chat run on identical retrieval and memory, so any difference comes from the model itself.

quality

Tested and measurable

21 unit tests, a terminal and a browser chat interface, and an evaluation harness with BLEU, ROUGE, BERTScore, retrieval precision and recall, a groundedness check and latency, on an 18-question hand-labelled set.

what I learned

Decisions that came from real failures.

Small models often ignored an instruction to say "I don't know", so I moved that rule into code. Passing every retrieved chunk made the model contradict itself, so I measured scores and set a cut-off in the gap between relevant and off-topic matches. Follow-up questions failed until the previous turn was added to the search.

It is a research prototype on a small, synthetic knowledge base of six documents, so I make no claims about large-scale performance. It is the same habit I bring to mock interviews: say what you built, why, and where it breaks.
